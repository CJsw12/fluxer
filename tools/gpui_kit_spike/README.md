# gpui_kit_spike

`gpui-kit =0.10.0`(내부적으로 `gpui-pre =0.3.12`) 조합으로 Fluxer 메인 UI를 만들 수 있는지 보는 두 번째 시제품입니다. 독립 Cargo 워크스페이스이며 `tools/gpui_spike`(gpui 0.2.2)와 같은 구조로 수치를 비교하기 위한 것입니다.

- 위쪽: 합성 메시지 5만 개(굵게, 코드블록, 인라인 코드, 링크, 목록, 한글, 이모지 / 1~10줄)를 `MessageScroller`(gpui `list` 기반 가변 높이 가상 목록)로 표시합니다. 본문은 `TextView::markdown(..).selectable(true)`입니다. 맨 아래(tail follow)부터 시작합니다.
- 아래쪽: `gpui_kit::component::input::Input` + `InputState`. Enter로 목록 끝에 추가하고 맨 아래로 스크롤합니다. IME 조합 중(`marked_text_range` 존재)이면 전송하지 않습니다.

`v_virtual_list`는 모든 행 높이를 미리 알아야 해서(`item_sizes: Rc<Vec<Size>>`) 줄바꿈 마크다운 높이를 모르는 채팅 목록에는 맞지 않아 쓰지 않았습니다.

## 빌드와 실행

```
cd tools/gpui_kit_spike
set CARGO_TARGET_DIR=%REPO%\target\gpui_kit_spike
cargo build --release
..\..\target\gpui_kit_spike\release\gpui_kit_spike.exe                    :: 수동 확인용
..\..\target\gpui_kit_spike\release\gpui_kit_spike.exe --bench            :: 마크다운 행 자동 스크롤 후 종료
..\..\target\gpui_kit_spike\release\gpui_kit_spike.exe --bench-plain      :: 일반 텍스트 행 자동 스크롤 후 종료
..\..\target\gpui_kit_spike\release\gpui_kit_spike.exe --bench --step=40  :: 프레임당 스크롤 행 수(기본 12)
```

bench는 맨 위로 이동한 뒤 프레임마다 `step`개 행만큼 `scroll_to_offset`으로 끝까지 이동합니다. `MessageScrollerState`가 픽셀 단위 `scroll_by`를 노출하지 않아 gpui_spike의 `--step=<px>`와는 단위가 다릅니다. plain 모드 본문은 같은 마크다운 원문을 가공 없이 일반 텍스트로 표시합니다.

## 측정 결과 (2026-11-17, release, 900x700 창, 1회 실행)

| 모드 | step(행) | 경과 ms | render 수 | 프레임 간격 p50 / p99 / max (ms) | 시작 private / peak WS (MB) | 종료 private / peak WS (MB) |
| --- | --- | --- | --- | --- | --- | --- |
| `--bench` (markdown) | 12 | 13347 | 4164 | 3.12 / 5.29 / 44.32 | 113.7 / 112.0 | 156.3 / 163.1 |
| `--bench-plain` | 12 | 13441 | 4164 | 3.14 / 5.35 / 6.37 | 78.2 / 70.3 | 91.6 / 83.6 |
| `--bench` (markdown) | 40 | 3999 | 1249 | 3.13 / 5.28 / 10.64 | - | 114.9 / 106.6 |
| `--bench-plain` | 40 | 4028 | 1249 | 3.14 / 4.96 / 6.07 | - | 90.8 / 83.2 |

해석 주의: 프레임 간격이 마크다운과 plain 모두 약 3.1ms(약 310fps)로 고정되어 있어 프레임 페이싱이 지배적입니다. 이 수치만으로 마크다운 렌더 CPU 비용 차이를 단정할 수 없고, 차이는 메모리(시작 +35MB, 종료 +65MB)와 max 간격에서만 보입니다. 이 bench는 행 점프 스크롤이라 중간 행 높이를 전부 측정하지 않으며, 실제 휠 스크롤의 체감 부드러움은 사람이 확인해야 합니다. gpui_spike(2만 행, 픽셀 스크롤)와는 행 수와 스크롤 단위가 달라 직접 비교가 아닌 참고용입니다.

## 한글 IME 수동 확인 체크리스트 (미검증)

Microsoft 한글 IME를 켠 상태로 실행 파일(`--bench` 없이)을 띄워 하단 입력창에 입력합니다.

1. 조합 중 표시: `ㅎ`, `ㅏ`, `ㄴ`을 차례로 눌러 조합 중 글자가 구분(밑줄 등)되어 표시되고 확정 후 사라지는지 확인합니다.
2. 후보창 위치: 한자 키나 이모지 패널(Win+.)을 열어 후보창이 입력창 커서 근처에 뜨고, 글자가 늘어나면 따라 이동하는지 확인합니다.
3. 백스페이스 자모 삭제: 조합 중 `한`에서 백스페이스를 누르면 `하`, `ㅎ`, 빈 상태 순으로 줄어드는지 확인합니다.
4. 조합 중 Enter: 조합 중인 글자가 있을 때 Enter가 글자만 확정하고 메시지를 전송하지 않는지, 한 번 더 Enter를 누르면 전송되어 목록 맨 아래에 추가되는지 확인합니다.
5. 조합 중 포커스 이탈: 조합 중 다른 창으로 전환하거나 목록을 클릭했을 때 조합 글자가 유실, 중복, 깨짐 없이 확정되는지 확인합니다.
6. Ctrl+C / Ctrl+V: 입력창 선택 후 복사, 붙여넣기가 되는지, 한글과 이모지가 포함된 문자열이 깨지지 않는지 확인합니다.
7. 전송 후 목록이 맨 아래로 이동하는지, 창 크기를 바꿀 때 행 높이가 다시 계산되는지 확인합니다.

## 마크다운 텍스트 선택 확인 (미검증)

1. 메시지 본문에서 마우스 드래그로 한글, 영문, 이모지 구간이 선택(하이라이트)되는지 확인합니다.
2. 선택 후 Ctrl+C로 복사해 입력창이나 메모장에 붙여넣었을 때 내용이 보이는 텍스트와 일치하는지 확인합니다.
3. 코드블록, 인라인 코드, 목록 항목을 포함해 드래그했을 때 선택과 복사가 되는지 확인합니다.
4. 여러 메시지(행)에 걸친 드래그 선택이 되는지 확인합니다(행마다 별도 `TextView`라 안 될 수 있음).
5. 링크 클릭 동작과 드래그 선택이 충돌하지 않는지 확인합니다.

### 드래그 선택 헤드리스 테스트 (2026-11-17)

`cargo test`(dev-dependency `gpui-pre =0.3.12` `test-support`)가 실제 `Root`를 `base::Root`로 감싼 가상 창에서 입력창에 포커스를 둔 채 드래그를 시뮬레이션합니다.

- `synthetic_message_body_is_drag_selectable`: 합성 메시지 행을 왼쪽 여백에서 줄 끝 너머까지 끌면 선택 텍스트가 생깁니다.
- `submitted_message_body_is_drag_selectable`: 입력창에 쓰고 Enter로 보낸 행을 같은 방식으로 끌면 보낸 문장이 선택됩니다.

조사 결과 원본 코드(수정 없음)에서 두 테스트가 모두 통과했고, 여러 행에 걸친 위·아래 방향 드래그도 텍스트를 반환했습니다. 헤드리스 환경에서는 "목록 메시지가 선택되지 않는다"는 증상이 재현되지 않았습니다. 예외는 하나뿐이었습니다. 텍스트 밖(왼쪽 여백)에서 누른 뒤 중간 MouseMove 없이 곧바로 텍스트 밖(줄 끝 너머)에서 놓으면 아무것도 선택되지 않습니다. 실제 마우스는 중간 이동 이벤트를 보내므로 사용자 증상의 원인으로 보기 어렵습니다. 행 머리(작성자, 시각)는 일반 `div`라 그 글자 자체는 선택 대상이 아닙니다.
